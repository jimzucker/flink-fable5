WHY (fairness gap found in review)
----------------------------------
Phase 10 tuned AWS against Confluent's 232.7k — but that Confluent number
was itself probably not a ceiling:
1. The drained topic (prices-bulk) had only 16 buckets while tuned AWS ran
   48 partitions — Confluent's source parallelism was likely bucket-capped.
2. The autoscaler used 16 of 20 CFUs — consistent with partition-bound,
   not compute-bound.
3. The emission-conflation trick (AWS Rung B, +36%) ports to SQL as
   windowed last-row emission on the position statements.
What Confluent likely cannot close: the unit-price gap ($0.21/CFU vs
$0.11/KPU): cost-floor parity would need ~2x AWS's per-unit throughput.
The project ethos caught ourselves: never compare one system's cruise to
another's sprint — in either direction.

RESULTS
-------
REMATCH A (48-bucket source, cap-40 pool): 287k peak, 16 CFUs elected —
  +23% over the bucket-capped 232.7k. The old number WAS partition-bound.
REMATCH C (scaling proof, real cap-10 pool): 265.5k at 10 CFUs = 93% of the
  16-CFU result. Confluent's CFU dial SATURATES for a single statement.
DEPLOYABILITY AUDIT (real cap-20 pool — the claimable config): 301.7k peak,
  10 CFUs elected. ("16 CFUs" was never buyable: max_cfu enum is
  {5,10,20,30,40,50} and can never be lowered on an existing pool.)
CARDINALITY (the real lever): same statement/pool, 10 symbols -> 301.7k;
  30 symbols -> 386.3k (+28%). The window parallelizes across KEYS.
REMATCH D (sharding, 2 statements x 2 pools, disjoint half-topics): 235.7k
  COMBINED — LESS than one statement alone. Splitting 10 symbols 5+5 halved
  each shard's parallelism. Sharding only helps if the key space is wide.
REMATCH B (full pipeline, all 6 statements, cap-20): 127k sustained at 15
  CFUs vs AWS's 435k for the same logical work. Architectural: Confluent
  statements hand off through Kafka (dedup output re-read 4x); AWS operators
  pass in memory inside one job.
LATENCY (same probe, same method, 11k/s live feed) — THE HEADLINE:
  AWS       p50   267ms  p95   453ms  p99   495ms  max 1,058ms
  Confluent p50 33,029ms p95 41,217ms p99 44,213ms max 47,225ms  = 124x
SOAK 28 min: AWS mean 232,705/s with stdev 30/s (0.01% jitter), 0 restarts.
  Confluent ping-pong mean 360.9k/s, stdev 63.9k (autoscaler breathing).
RECOVERY: AWS snapshot-restore under load -> 198,313 MV records re-verified
  net_qty x price EXACT, 0 mismatches. Confluent statement stopped 30s
  mid-flow, resumed with state, re-validated with the 5-check suite.
VARIANCE: Confluent ceiling 265k/287k/302k (+-13%); AWS floor 352k/344k
  (2%); AWS 8-KPU failed twice (199k, 220k) — the floor is 10 KPUs, not 8,
  outside any variance explanation.
TEARDOWN: AWS destroyed, zeros verified (2 orphaned MSF ENIs deleted by hand
  again — repeatable behavior, now in the runbook). Confluent destroyed,
  zeros verified (only the built-in 'default' env remains; destroying the
  environment cascaded the two API-created experiment pools).

ONE HONEST GAP: the FINAL post-recovery re-validation on Confluent was cut
short by the auto-teardown (my scheduling bug: macOS has no `timeout`, so
the wait-for-validation loop fell through). What IS proven for Confluent
recovery: the statement stopped 30s mid-flow and returned to RUNNING, and
the validation immediately after showed dedup PASS across 5,614,275 trade
records with 280,501 duplicates absorbed — which is precisely the
state-survival proof (had dedup state been lost, duplicates would have
leaked). Completeness and both MV checks also passed; only the two position
checks were still mid-convergence in the usual checkpoint-lag pattern.
AWS's recovery was fully verified: 198,313 outputs re-checked exact after
snapshot restore.

VERDICT: AWS wins throughput (3.4x full pipeline), latency (124x), cost
(~40% lower TCO at equal work) and steadiness (stdev 30 vs 63.9k).
Confluent wins build/operate simplicity: ~200 lines of SQL vs ~2,000 of
Java, no jar, no VPC, no images. It is an ARCHITECTURE difference, not a
product verdict — in-memory operator handoff vs Kafka between every step.
Choose by latency budget: sub-second -> DataStream; multi-second-tolerant
analytics -> SQL, built ~10x faster.
