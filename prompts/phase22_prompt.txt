PHASE 22 — like-for-like: local vs AWS vs Confluent
====================================================
User: "close phase 21 and make aws and confluent test a new phase"
User: "goal of the new phase is to do a like for like aws/confluent to local"

GOAL
  Same config, same feed, same measurements, in all three environments, in ONE
  table. Every cross-environment number published so far was measured a
  different way in each place -- that is what forced the retractions. Fix the
  method first, measure second.

WHAT MUST BE IDENTICAL
  config      SQL conflate=0 emit=1000 / DataStream salt=8 emit=1000
  feed        200 symbols, 2,000 prices/s, 200 trades/s, adaptive, 30% IPO
  partitions  16 everywhere   (local is 4 -- must raise)
  parallelism 8 everywhere    (local is 4 slots -- must raise)
  measures    six checks, ordering checks, staleness percentiles, in/out rates

NOT COMPARABLE, AND THE TABLE MUST SAY SO
  Local throughput is source-bound at ~5-6k rec/s (measured 31% busy, 0%
  backpressure at P=2 and P=4 during a drain). Local gives correctness,
  ordering, staleness and volume -- NOT capacity.

CARRIED IN FROM PHASE 21
  Working configs, validated locally, both engines:
    SQL:        sql.price.conflate.ms=0, mv.emit.interval.ms=1000
    DataStream: price.salt.factor=8,     mv.emit.interval.ms=1000
  Both: 100% exact market values, 0ms staleness, zero ordering violations.

  Rule: reduce the OUTPUT, never the INPUT. An output reduce publishes the
  newest value less often; an input reduce (tumbling window) throws the newest
  value away.

TWO KNOWN DEFECTS IN THE PUBLISHED AWS NUMBERS
  1. Every AWS SQL figure ran with input reduce ON and output reduce OFF --
     backwards on both. SQL published 3x more records than necessary, so its
     throughput is understated and the DataStream-vs-SQL gap is overstated.
  2. AWS DataStream ran with price.salt.factor=1, the vulnerable default. Final
     values were correct but in-flight ordering was never checked; the ordering
     check did not exist yet.

STEPS
  1. Change price.salt.factor default 1 -> 8, re-verify locally (free).
  2. AWS correctness at scale, both working configs (~$3). First time the
     ordering check runs on AWS.
  3. AWS throughput on the working SQL config vs the 6,106 rec/s on record
     for the broken one (~$4). Decides whether the gap survives.
  4. Confluent (~$3) -- but NOT yet reachable:
       * terraform deploys dml/ files individually and never references a
         statement set, so confluent/sql/working/statement_set.sql needs a new
         resource.
       * UNVERIFIED whether Confluent exposes an output reduce at all. AWS uses
         the upsert-kafka option sink.buffer-flush.interval; Confluent uses
         managed tables. Test with a CREATE TABLE before assuming.
       * If not expressible, THAT is the finding -- the fix is half portable,
         which beats another throughput number.

PRE-DECLARED INTERPRETATION
  SQL working config materially beats 6,106 rec/s -> restate the published gap.
  No material change -> the gap stands; conflation affects correctness only.
  Confluent cannot express the output reduce -> platform capability finding.
