PHASE 20 — WHY DOESN'T FLINK SQL SCALE?
=======================================
User: "ok new phase whats are plan to figure out why SQL doesnt scale?"
      "ok, run w/o prompting me"

Phase 19 established THAT SQL does not convert added compute into throughput on
either cloud. It did not establish WHY, and every measurement so far has been
whole-pipeline, which cannot identify which stage refuses to parallelise.

LEADING HYPOTHESIS, and we built it ourselves: the realistic market puts ONE IPO
symbol at 30% of the tape. Flink sends one key to one worker, so a single subtask
owns 30% of the work regardless of parallelism -- Amdahl's law caps speedup at
~3.3x. That would look exactly like "SQL doesn't scale", and would mean the
finding is mis-stated.

Counter-evidence: DataStream ran the SAME skewed feed and sustained 5.5x. So skew
is likely a factor, not the whole story. Experiment D (DataStream scaling on the
same feed) is the control that separates "the workload can't scale" from "SQL
can't scale it".

Plan in docs/PHASE20_PLAN.md. Diagnosis first (per-operator backpressure and
subtask skew), then one-variable experiments.

STEP 1 RESULT — H1 (hot-key skew) REJECTED BY MEASUREMENT
==========================================================
Per-operator profile, SQL at P=20, saturating load, 3,000 symbols with a 30% IPO:

  operator                              bp%   busy max%  busy avg%  skew
  Source: prices -> Calc -> Window     56.3      67.0       48.0     1.4
  GroupAggregate_7 -> Calc             0.0      100.0       99.8     1.0
  GroupAggregate_12 -> Calc            2.9      100.0       99.0     1.0
  SinkMaterializer_33 -> mv_by_account 0.0       98.6       77.9     1.3
  Join_31 -> Calc                     12.0       94.5       58.2     1.6
  Deduplicate_28                       0.0       74.6       27.8     2.7

EVERY skew ratio is 1.0-2.7. No operator has one worker carrying the stage, so
the 30% IPO key is NOT the ceiling. The leading hypothesis was wrong and would
have survived indefinitely without per-operator visibility -- every previous
measurement was a pipeline average, which cannot show one overloaded worker
either way.

THE ACTUAL BOTTLENECK: the GroupAggregate operators, at 99-100% busy on EVERY
subtask. Uniformly saturated, not skewed. The prices source is backpressured
56% because those aggregates cannot accept more.

H2 IS REAL: SinkMaterializer_33 runs at 78% average busy. That is the operator
the unresolved upsert key inserts, and DataStream does not have it at all.

LIKELY MECHANISM: the aggregates sit on an UPDATING stream, so each input change
propagates as a retract + insert pair, and the materializer adds another
stateful correction. SQL performs several times the work per input record that
DataStream does. That explains lower throughput directly.

STILL OPEN: uniform saturation at P=20 does not by itself explain failure to
scale -- if all 20 subtasks are pinned, 40 should help. Next measurement is the
same profile at P=40. If GroupAggregate busy% DROPS, the stage scaled and the
limit is elsewhere (source, or the metric). If it stays at ~100%, the work per
subtask is not decreasing with parallelism, which is the real finding.

NOTE ON THE HARNESS: the first three profile attempts returned "no per-operator
data". The SEARCH expression named dimensions {Application,Task,TaskOperator};
the metrics only carry {Application,Task}. SEARCH requires an exact
dimension-set match, so naming a dimension that does not exist matches nothing
and returns an empty result that reads exactly like "the job isn't running".

STEP 1b — SAME PROFILE AT P=40: THE MECHANISM
==============================================
  operator                              bp%   busy max%  busy avg%  skew
  Source: prices -> Calc -> Window     98.8       4.7        1.2     3.9
  GroupAggregate_12 -> Calc             6.1     100.0       76.3     1.3
  GroupAggregate_7 -> Calc              0.0     100.0       74.5     1.3
  Join_38 -> Calc                       0.0     100.0       70.8     1.4
  SinkMaterializer_33                   0.0      99.0       65.3     1.5
  Join_31 -> Calc                       0.0      97.7       68.6     1.4

The prices source is now 98.8% BACKPRESSURED while doing 1.2% work: it is not
the limit, it is being held back. Skew flags appear only on operators that are
nearly idle (Deduplicate at 20% busy, source at 4.7%) -- skew on an idle
operator does not govern anything, so H1 stays rejected at P=40 too.

WHAT DOUBLING PARALLELISM ACTUALLY BOUGHT
  GroupAggregate busy avg fell 99% -> 75%, so the stage DID divide its work.
  But throughput rose only 1,659/s -> 1,948/s (Phase 19, +17%).

  total busy-time    P=20: 20 x 0.99 = 19.8      P=40: 40 x 0.75 = 30.0
  per record/s       19.8/1659 = 0.0119          30.0/1948 = 0.0154   (+29%)

Doubling parallelism made each record ~29% MORE expensive in CPU-time. The added
workers did not go to waste idling -- they went to overhead: more state
instances, more network shuffles, more serialization between subtasks. That is
why +83% billed compute returned +17% throughput.

And busy MAX stays pinned at 100% on four operators at BOTH parallelisms while
avg drops. Throughput is governed by the slowest subtask, not the average one.
Adding subtasks adds more chances for one to be slow; it does not lower the max.

H2 CONFIRMED AS A CONTRIBUTOR, NOT THE CAUSE: SinkMaterializer_33 runs at 99%
max / 65% avg busy. Real cost, and an operator DataStream does not have at all.
Experiment B (materialize=NONE) will size it.

MEASUREMENT NOTE: Phase 20 defines its own throughput metric and re-measures
every condition with it, rather than inheriting Phase 19's. The unit is records
INGESTED at the sources. Counting records emitted would inflate SQL ~2x for free,
because SQL on an updating stream emits a retract AND an insert per change --
the very amplification under investigation. Phase 19's numbers are kept only for
the P=20 vs P=40 ratio quoted above.

PRE-DECLARED STATISTIC (recorded 19:05Z, after condition 1, before conditions 2-5)
==================================================================================
Condition 1 came back median=151/s but max=1,312/s -- the max is ~9x the median.
The pipeline is severely backpressured and therefore bursty.

For CAPACITY under saturation the correct aggregate is total records / total
time, which is the MEAN of the per-minute samples, not the median. The median
discards the bursts, but the bursts are real work the pipeline actually did.
Median is the right robust statistic for a noisy *steady* rate; it is the wrong
one for integrating a bursty one.

So the primary number for every condition is TOTAL MEAN = sum of the per-task
mean rates, which phase20_rate.py already prints per source task for every
condition. No script change is needed and none will be made mid-chain --
changing the harness between conditions would make them incomparable, which is
exactly the trap that produced the withdrawn Phase 19 numbers.

  condition 1, sql-P40:  285 (prices) + 70 (trades) = 355/s   <-- primary
                         median 151/s                          <-- secondary

Declared BEFORE the SQL P=20 and DataStream numbers exist, so the choice cannot
be fitted to a preferred conclusion.

STOPPING RULE, also declared now: within-run spread here is far worse than the
+/-25% run-to-run rule this project already operates under. If the SQL scaling
ratio and the DataStream scaling ratio differ by less than that spread, the
honest report is "this measurement cannot resolve the difference" -- NOT a
ratio. A number that cannot survive its own noise is not a result.

EXPERIMENT B RESULT — MATERIALIZER COSTS 46% OF THROUGHPUT (PROVISIONAL)
========================================================================
  condition                        primary (integrated)   median
  sql-P40                          285+70  =  355/s        151/s
  sql-P40-nomat                    450+212 =  662/s        697/s
                                   ------- 1.86x -------

Verified the config actually took effect: zero SinkMaterializer operators remain
in the P=40-nomat plan (grep count 0), vs one at 99% max / 65% avg busy with it
on. This is not a config that was silently ignored.

H2 is confirmed as a MAJOR contributor, not a minor one. The
SinkUpsertMaterializer -- present only because mv-by-account-ticker carries an
unresolved upsert key -- was consuming ~46% of throughput. DataStream has no
such operator, so a real slice of the "SQL is 5.5x slower" gap is this one
fixable defect rather than anything intrinsic to SQL.

*** THIS SPEEDUP IS NOT CLAIMABLE YET ***
Flink inserts that materializer PRECISELY BECAUSE the planner cannot prove the
upsert key matches the primary key. Setting it to NONE deletes the operator that
was repairing out-of-order updates. The plausible failure is silent: final
market values that are wrong, with the job healthy and fast.

That is exactly the case the standing rule governs -- correctness and
completeness BEFORE performance; fast only counts if the numbers are correct. A
1.86x number obtained by deleting the correctness operator is the single easiest
way to publish a fast wrong answer, so it is recorded as PROVISIONAL and gated
on validation.

REQUIRED BEFORE THIS BECOMES A RESULT: run the six-check validator against the
nomat config and confirm final market value = final price x correct position.
  - validator PASSES -> 1.86x is a real, free win; resolve the upsert key
    properly and keep it.
  - validator FAILS  -> the finding becomes "the materializer costs 46% and
    cannot be safely removed; the fix is to resolve the upsert key so the
    planner never inserts it."
Both outcomes are publishable. Neither is known yet.

RETRACTION — THE SCALING METRIC WAS DIVIDING BY PARALLELISM
=============================================================================
MSF publishes numRecordsOutPerSecond once per SUBTASK under the same
{Application,Task} dimensions. Reading it with stat "Average" therefore averages
ACROSS SUBTASKS and returns a PER-SUBTASK rate, not a total.

That is the worst possible error for a scaling study, because the quantity is
normalized by the very variable under test: under PERFECT linear scaling a
per-subtask average stays FLAT, and under real scaling it FALLS.

  total = per-subtask average x subtask count

Caught it because ds-P20 returned an implausibly tight spread (586/597/614)
for a saturated pipeline, and because trades read 20.0/subtask x 20 = exactly
400/s -- precisely the 4 x 100/s the generators are configured to emit. That
exact match is the ground truth that proved the multiplier.

CORRECTED TOTALS (recomputed from raw CloudWatch, scripts/phase20_totals.py)
  sql-P20            7,690 rec/s
  sql-P40           13,405 rec/s     -> SQL scales 1.74x
  sql-P40-nomat     25,387 rec/s     -> materializer costs 1.89x at fixed P
  ds-P20            11,421 rec/s     (trades caught up at exactly 400/s)
  ds-P40            35,058 rec/s     (trades draining 19,791/s of backlog)

WITHDRAWN:
  "SQL doesn't scale -- 0.98x, doubling bought nothing"
      -> WRONG. SQL scales 1.74x. Artifact of dividing by parallelism.
  "Doubling parallelism raises per-record cost +29%"
      -> WRONG, and derived from the same bad numbers. Recomputed, per-record
         cost FELL ~22% (0.00272 -> 0.00211 busy-units per record/s).

EXPERIMENT D IS INVALID — I VIOLATED A DOCUMENTED METHOD RULE
=============================================================================
ds-P20 ran with trades at exactly 400/s: FULLY CAUGHT UP. A caught-up pipeline
reports its ARRIVAL RATE, not its capacity -- at P=20 DataStream had spare
capacity it never used, because only 400 trades/s were arriving. ds-P40 was
draining 19,791/s of accumulated trades backlog. The two conditions measured
different quantities, so the apparent 3.07x "DataStream scaling" is an artifact.

ROOT CAUSE: the chain ran generators continuously across all five conditions and
never purged topics between them, so backlog grew monotonically and every
condition started from a different state. The method rules carried forward at
the bottom of PHASE20_PLAN.md say, verbatim, "purge between runs." I wrote that
rule into the plan and then built a chain that ignored it.

CONSEQUENCE: Phase 19's "SQL doesn't scale" headline is now UNSUPPORTED rather
than disproven. D was the control meant to settle it and it did not return a
valid answer. Not substituting a DataStream-vs-SQL verdict that was not earned.

WHAT SURVIVES THE BUG (all independent of the metric):
  * H1 REJECTED -- per-operator busy max-vs-avg, unaffected by totals.
  * Materializer ~1.89x -- both conditions at the SAME parallelism, so the
    per-subtask normalization cancels. Still gated on correctness validation.
  * Price-ordering defect in MarketValueByAccountTicker:91-93 -- code-level.

REQUIRED FOR THE RERUN:
  1. Purge topics between conditions (topics_recreate, or explicit delete).
  2. Saturate BOTH streams -- raise trades/sec so no baseline sits caught-up.
     A condition that keeps up is measuring the generator, not the pipeline.
  3. Report totals via phase20_totals.py, never per-subtask averages.
  4. Randomize or alternate condition order so backlog drift cannot align with
     the variable under test.

V1 RESULT — ORDERING GUARD VALIDATED, AND THE BUG WAS LIVE
===========================================================
DataStream, adaptive keys, 200 symbols with a 30% IPO, simple numbers
(qty=1, symbol i priced $(i+1) rising 1 cent/tick).

  streamed: trades=86,600 prices=866,000 symbols=200
  [PASS] dedup: 4,608 duplicates, 81,992 unique of 86,600
  [PASS] positions by account+ticker: 1,000 keys, 0 mismatched
  [PASS] positions by ticker: 200 keys, 0 mismatched
  [PASS] completeness sum(accounts)==ticker: 0 disagree
  [PASS] MV by account == position x FINAL price: 1,000 checked, 0 wrong
  [PASS] MV by ticker  == position x FINAL price:   200 checked, 0 wrong

  demoStaleTicksDropped: 461,523

461,523 of 866,000 prices -- MORE THAN HALF -- arrived out of order and were
rejected by the new guard. This is not a rare race being defended against; it is
the majority case on a salted feed, which is what adaptive keying does BY DESIGN
to break the IPO hotspot.

WHY THIS PASS IS ADMISSIBLE AND THE PHASE 18 PASS WAS NOT:
Phase 18 ran these same six checks against a STATIC price per symbol and passed
with NO event-time guard anywhere in the code. Identical values cannot reveal a
reordering, so the checks could not have failed -- they were not evidence. Now
prices move monotonically, the violation demonstrably occurs 461k times, and the
market-value checks still come out exact. The test had a real chance to fail.

It also confirms retroactively that the defect was LIVE, not theoretical: those
461,523 ticks were previously overwriting newer prices unchallenged. Every market
value published from the DataStream path on a salted feed was suspect.

(55 and 7 rows classified "conflation lag" -- the validator's benign category
where the observed price range explains the difference; not errors.)

V2 / V3 — INCONCLUSIVE ON MARKET-VALUE CORRECTNESS (tolerance was vacuous)
==========================================================================
  V2 sql-mat   : 1,000/1,000 and 200/200 keys in "conflation lag", 0 exact
  V3 sql-nomat : 1,000/1,000 and 200/200 keys in "conflation lag", 0 exact

Both report "VALIDATION PASSED", and neither pass means anything for market
values. The lag rule accepted any implied price inside the symbol's WHOLE-RUN
min/max. With prices now moving monotonically that range spans the entire run,
so every price the pipeline ever emitted is accepted -- the check cannot tell
250ms of lag from minutes of staleness.

Note the symmetry of the two failures, because it is the actual lesson:
  Phase 18, static prices  -> tolerance width ZERO, but nothing could differ.
  Phase 20, monotonic      -> differences occur, but tolerance is the whole run.
Both configurations passed every check. NEITHER COULD HAVE FAILED. Widening the
signal without bounding the tolerance just moved the vacuum.

FIXED: validator now keeps a per-symbol deque of ticks within validate.lag.ms
(default 2000) of that symbol's newest tick and accepts only implied prices
inside that window. Acceptable staleness is a property of the conflation
interval, not of run length.

V1 IS UNAFFECTED: 945 of 1,000 keys matched EXACTLY and never touched the
tolerance. The DataStream ordering guard result stands.

COUNTER CONTAMINATION CONFIRMED (and self-corrected):
  V2 reported demoStaleTicksDropped = 580,867
  V3 reported demoStaleTicksDropped = 0
SQL mode does not run MarketValueByAccountTicker/ByTicker at all, so 0 is the
only correct SQL-mode reading. V2's figure was V1's DataStream run bleeding
through the counter's 25-minute lookback. Diagnosed from the metric's own
inconsistency and confirmed by V3 one condition later.

CONSEQUENCE: the 1.89x materializer result remains UNCLAIMED. Whether removing
the materializer is safe is still untested -- both attempts to test it used a
check that could not fail.
