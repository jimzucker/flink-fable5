KNOWN GAPS IN CELL B (recorded, not hidden)
--------------------------------------------
- Dedup state has NO TTL in SQL: table.exec.state.ttl is job-wide and
  would also expire the position aggregates (silently changing answers);
  the STATE_TTL hint does not cover deduplication. So the SQL job's
  trade_id state grows unbounded. Exposed as sql.state.ttl.ms default 0.
- No operator uids in SQL; savepoint restore across a topology change
  needs CompiledPlan.
- positions as_of is MAX(event_time), not last-applied event time (same
  substitution the proven Confluent SQL makes).
- Account-level sinks get an extra SinkUpsertMaterializer because the
  planner cannot prove CONCAT(account,'|',ticker) is a bijection of the
  group key — extra state the DataStream job does not carry.

15.3a THE BLOCKER, AND WHAT IT COST
------------------------------------
Switching the DataStream sink to EXACTLY_ONCE (the user's correctness point:
every prior comparison pitted our at-least-once pipeline against Confluent's
exactly-once one, so it measured the guarantee as much as the engine) made
the job CRASH-LOOP: restarts climbing forever, ZERO checkpoints ever
completed, therefore zero committed transactions, therefore probes reading
"NO RECORDS OBSERVED".

Four attempts at parallelism 20 produced no attributable information because
I changed four things at once (new jar, new guarantee, new checkpoint
interval, new dedup TTL). Two second-order traps made it worse:
  * MSF refuses to update an application it cannot snapshot, and cannot
    snapshot a crash-looping one — so a broken app CANNOT be fixed in place.
    Every attempt needed stop -> apply -> start, and the isolating control
    experiment was literally unrunnable. Fixed by making snapshots_enabled a
    variable and turning it off while debugging.
  * MSF surfaces NO useful error for this failure (it happens inside Kafka
    producer initialization, not Flink code), so the logs look like healthy
    startup noise.

ROOT CAUSE (found by dropping to parallelism 2 / 10 msgs-per-sec — $1/hr —
with a known-good control and changing ONE variable at a time):
  MSK IAM auth requires THREE permissions beyond WriteData/ReadData for
  transactional producers —
    kafka-cluster:WriteDataIdempotently
    kafka-cluster:AlterTransactionalId
    kafka-cluster:DescribeTransactionalId
  plus a resource ARN for transactional-id/<cluster>/<uuid>/*.
  Without them the producer cannot initialize its transaction and the job
  dies, IDENTICALLY at parallelism 2 with 10 msgs/sec and at parallelism 20
  with 11k, at any checkpoint interval and any transaction.timeout.ms.
  After the fix: restarts 0, records flowing, at both scales.
  (transaction.timeout.ms <= MSK's transaction.max.timeout.ms — broker
  default 15 min vs Flink's producer default of 1 HOUR — is also required,
  but is NOT sufficient on its own.)

IMPORTANT: the wrong conclusion was available and I nearly published it.
"Exactly-once does not work on Managed Flink for this pipeline" and "we
never granted the permissions exactly-once needs" look identical from
outside — crash loop, no output, no error — but only one of them is true.

TUNING HYPOTHESIS TESTED AND REJECTED: the plan inserts a
SinkUpsertMaterializer because the planner cannot prove

CONFLUENT WARNS ABOUT THE SAME DEFECT AWS HIDES (user spotted in console)
--------------------------------------------------------------------------
Confluent flags dml-14-mv-by-account-ticker with:
  UPSERT_AND_PRIMARY_KEYS_DIFFERENT — "The primary key does not match the
  upsert key derived from the query ... the system needs to add a
  state-intensive operation for correction."
  HIGH_STATE_OPERATOR_WITHOUT_TTL — "potentially needs to store an infinite
  amount of state ... can result in a DEGRADED statement and higher CFU
  consumption."

This is EXACTLY the AWS SinkUpsertMaterializer, same root cause: the sink PK
is CONCAT(account,'|',ticker) but the GROUP BY is on (account, ticker), so
the planner cannot prove the sink key derives from the grouping key and
inserts a correction operator.

THE DIFFERENCE IS OBSERVABILITY, and it favours Confluent:
  Confluent  — named warning, in the console, with a doc link, and an
               explicit statement that it costs CFUs.
  AWS        — silent. Found only by reading the execution plan and noticing
               a task named SinkMaterializer_24 moving 219k records/sec.
Add to the matrix: Confluent surfaces query-shape problems that MSF hides.

FIX (untested on either platform): group by the concatenation itself so the
upsert key EQUALS the primary key —
   GROUP BY CONCAT(account,'|',ticker)   instead of   GROUP BY account, ticker
On AWS the equivalent (upsert-materialize=NONE) removed the operator
entirely but bought only ~14%, so expect a modest gain, not a fix for the
~19x throughput gap.

TTL warning = the known SQL limitation: table.exec.state.ttl is JOB-WIDE, so
it cannot be scoped to dedup the way the DataStream job scopes
dedup.state.ttl.ms. Setting it would also expire the position aggregates and
silently change the answers. Unresolved.

GAP FOUND BY USER: THE AWS PIPELINE IS NOT SALTED
--------------------------------------------------------------------------
Question: "does the AWS test apply the same salted tuning?"  Answer: NO.

grep for salt|localAgg|two-phase|preAgg across src/main/java => ZERO hits.
The six AWS keyBy stages (PositionPipeline.java:99-143):
  :99   keyBy(p -> p.symbol)                  10 keys   NARROW  unsalted
  :103  keyBy(t -> t.tradeId)                 millions  wide
  :109  keyBy(t -> t.account + "|" + t.ticker) wide
  :120  keyBy(t -> t.ticker)                  10 keys   NARROW  unsalted
  :131  keyBy(p -> p.ticker)   <- MV by ACCOUNT+ticker  10 keys NARROW unsalted
  :143  keyBy(p -> p.ticker)                  10 keys   NARROW  unsalted

FOUR of six stages sit on a 10-value key space, including :131 — the heaviest
output (market value by account+ticker) is keyed by TICKER ALONE because it
has to join the broadcast-ish price stream. So the widest fan-out work in the
job funnels through 10 keys. This is the SAME key-starvation structure that
capped Confluent, and AWS never got the salting fix that Confluent got.

WHICH DIRECTION THIS BIASES:
  throughput / latency / cost — AWS won WITHOUT this tuning while Confluent
    had it. So AWS's margin is UNDERSTATED. Those conclusions stand and are
    conservative.
  SCALING — biased the other way and NOT safe. We were about to judge
    "once tuned, how does Confluent scale?" on a salted config while AWS's
    linear-scaling proof (phase 10.3b) was measured UNSALTED. With four
    stages pinned at 10 keys, AWS parallelism above ~10 cannot help those
    operators, so the AWS linear-scaling claim needs re-examination: either
    the ceiling was set elsewhere, or it holds only to about P=10.

=> "most tuned version of each" is NOT yet true for AWS. To close it, apply
   the same two-phase salt to the four narrow keyBy stages and re-run.

docs.confluent.io/cloud/current/flink/how-to-guides/resolve-common-query-problems.html

RUN A (AWS DataStream, tuned) — SEED METHODOLOGY
--------------------------------------------------------------------------
Backlog sizing is not a wall-clock decision, it is an arithmetic one:

    seed_records > drain_rate x (metric_blind_spot + plateau_needed)

Two seeds were REJECTED before producing any number:
  1. demo defaults (10 trades/s, 20 prices/s) -> ~14k records. Drains in about
     a second; anything measured would have been startup noise.
  2. one Fargate task at its 10,000/s target only achieved 5,683/s (CPU-bound)
     -> 3.44M records = 10-17s of drain. CloudWatch is 1-min granularity with
     a ~2-min blind spot after job start, so the drain would have ENDED before
     the first usable datapoint existed.

Fix is horizontal, not vertical: 12 generator tasks x 20 min. Once the work was
spread each task hit ~9,700 prices/s (vs 5,683 alone), aggregate ~116k/s, for
~140M prices + ~1.4M trades. At an expected 200-400k/s drain that is 6-11 min
of draining -- outlasts the blind spot with room for a stable plateau.

Config bugs caught by the audit//harness BEFORE any number was produced:
  * Confluent 6 buckets vs 10/20/40 CFUs  -> would have read as "cannot scale"
  * generator at demo rates               -> startup noise as throughput
  * topics_recreate=true                  -> MSK ThrottlingQuotaExceeded, the
                                             generator silently absent
  * arm64 image on x86 Fargate            -> exec-format error, reads as an app bug
  * audit's own ACCOUNTS=50 vs deployed 5 -> overstated cardinality 10x
None of these are visible in a throughput number. That is the whole argument
for auditing utilisation before trusting a measurement.

RUN A RESULTS — AWS DataStream, tuned, exactly-once, P=20 (~6 billed KPU)
--------------------------------------------------------------------------
Method: drain a seeded backlog, time start->completion, rate = records/elapsed.
Chosen over reading CloudWatch rates because MSF merges subtask series and the
aggregation semantics are ambiguous; records/elapsed assumes nothing. The
probe's x-parallelism scaling agreed within ~20%, which is the cross-check.

  SALTED (price.salt.factor=8)   143.68M records / 982s   = ~148,000 rec/s
  UNSALTED (price.salt.factor=1) ~140M records   / 2613s  = ~53,600 rec/s

CRITICAL: IDLE PARTITIONS STALL EVENT-TIME WATERMARKS (self-inflicted)
--------------------------------------------------------------------------
SYMPTOM: Confluent statement set RUNNING for an hour, consuming `prices` at up
to 7.15M/min (119k/s), writing ZERO rows to all four sinks. No error, no
DEGRADED, phase stayed RUNNING.

CAUSE: 10 tickers hashed into 48 buckets => at most 10 buckets ever carry data
and 38 are PERMANENTLY EMPTY. An empty partition never advances its watermark,
so the event-time TUMBLE never fires and no window ever closes. The job reads
for ever and emits nothing.

SELF-INFLICTED: raising buckets 6 -> 48 to remove the source-parallelism
ceiling is what created this. The rule "partitions >= parallelism" is only half
the story; the other half is that partitions ABOVE KEY CARDINALITY are dead
weight AND actively dangerous on an event-time pipeline.

FIX (verified): sql.tables.scan.idle-timeout=5000. Output appeared immediately
on all four sinks. Confluent accepts the option.

CONTAMINATES THE AWS SQL CELL: SQL-on-AWS ran the same event-time TUMBLE
(sql.price.conflate.ms=250) against 48-partition topics with the same 10
tickers. The CloudWatch dashboard captured at the time reads
"Volume out - bytes/sec per sink: No data available". So the ~54,400 rec/s
figure very likely measured READING, not end-to-end processing, and the
"DataStream is 2.69x faster than SQL" claim is NOT SOUND until re-run with
table.exec.source.idle-timeout set. I noticed the empty-sink panel, said I
would check it, and published the number anyway.

WHY DATASTREAM IS IMMUNE: it uses WatermarkStrategy.noWatermarks() and
processing-time timers throughout, so idle partitions cannot stall it. Both
DataStream numbers (salted ~146,300/s; unsalted control, 2.66x) stand.

META-LESSON, and the expensive one: EVERY cell was validated on the INPUT side
(records consumed, backpressure, restarts, checkpoints) and NEVER on the OUTPUT
side. A pipeline that reads fast and writes nothing scores beautifully on a
throughput metric. Assert non-zero SINK traffic before any drain number counts.

SCALING VERDICT — OVERTURNS THE PUBLISHED CONCLUSION
--------------------------------------------------------------------------
  cap-10  36,681,336 consumed / 695s = 52,779 rec/s
  cap-20  63,736,838 consumed / 807s = 78,980 rec/s
  => 1.50x throughput for 2x CFUs (75% scaling efficiency)
  Output verified non-zero on all four sinks at BOTH rungs.

Backlogs differed (36.7M vs 63.7M) so RATES were compared, not drain times --
cap-20 took LONGER in wall-clock (807s vs 695s) while being substantially
faster per second. Comparing times here would have inverted the conclusion.

WHAT THIS REPLACES: the earlier "10 -> 16 CFUs = +8%, the CFU dial saturates"
finding. That was measured with 6-BUCKET tables, where a Flink source cannot
use more than 6 subtasks however many CFUs are attached. Confluent was never
given the chance to scale. At 48 buckets it returns +50% for 2x compute.

WHY 1.50x AND NOT 2.0x -- and this is NOT a platform limit: four of six stages
key on TEN TICKERS. The salted conflation parallelises across 80 shard keys and
does scale; the downstream market-value stages stay pinned at ten and cannot
