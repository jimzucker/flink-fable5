PHASE 23 — 100 symbols, 2 -> 4 partitions, live vs backlog
===========================================================
User: "lets make plan starting with 100 unique symbols with 2 partitions for
source, output position/account/symbol and position/symbol then join prices and
output the same 2 keys market value, window prices tumbling window 250ms, ensure
completeness and correctness of each output and that we do not publish out of
sequence, then scale up to 4 partitions and produce status"
User: "lets run 2 cycle one producing and consuming, then run producers queue up
data, then run to see difference so 4 runs in this plan"

PIPELINE
  100 unique symbols; source partitions 2 then 4; prices on a 250ms TUMBLING
  window; outputs position/account/symbol and position/symbol, then join prices
  for market value on the SAME two keys.

FOUR RUNS
  1. 2 partitions, LIVE     (producer and consumer together)
  2. 2 partitions, BACKLOG  (queue all data first, then consume)
  3. 4 partitions, LIVE
  4. 4 partitions, BACKLOG

  Live and backlog measure different things: live is what the pipeline does when
  fed in real time, backlog is what it CAN do. Phase 21 showed local live runs
  are producer-bound, so both are needed.

CHECKS, EVERY RUN, EVERY OUTPUT
  completeness, correctness, no out-of-sequence publishing (as_of never
  backwards, no older price used after a newer one, no consumer left on a
  superseded value), staleness p50/p90/p99/max.

EXPECT UP FRONT
  A 250ms tumbling window on prices is exactly the config Phase 21 measured as
  producing ~2-3s stale market values, 0% exact -- the window discards the
  newest tick before it is used. The "MV == position x FINAL price" check is
  EXPECTED TO FAIL on all four runs. Staleness is therefore reported as a
  distribution, not pass/fail, so the runs stay comparable and the window's cost
  is quantified per partition count. Positions, completeness and ordering should
  pass regardless.

CARRIED-IN OPEN QUESTION
  Salt is a parallelism device and should not affect correctness, yet DataStream
  at price.salt.factor=1 published 490 of 500 keys with an out-of-order price
  while salt=8 published none. The event-time guard in the market-value
  operators should have prevented it either way. UNEXPLAINED -- run 1 exercises
  that path, so resolve it here.
