ANALYSIS
--------
The two "top ends" were measured differently. AWS's 110k msgs/s (P=12) was
INGEST-limited: 1:1 with the generator at ~52% busy — half the headroom
unused. Confluent's 232.7k was a CEILING measurement: backlog drain, no
ingest constraint. We compared AWS's cruising speed to Confluent's sprint.

Efficiency per dollar (list prices) already favors AWS:
  AWS:       ~12.1k msgs/s per KPU  @ $0.11/hr  -> ~110k msgs/s per $/hr
  Confluent: ~14.5k msgs/s per CFU  @ $0.21/hr  ->  ~69k msgs/s per $/hr
Confluent's 232k run burned $3.36/hr of compute. Brute-forcing 232k on AWS
(P~20) would cost $2.20/hr — cheaper, but the user's directive is better:
TUNE the pipeline so ~12 KPUs (~$1.40/hr) hits 232k. No scale-out.

Untapped levers (in plan order):
1. ParallelismPerKPU (the sleeper): we ran 1 subtask/KPU for clean ladder
   math; MSF allows up to 8 — more parallelism from the same billed KPUs.
2. More windows (user's ask): Phase 7 conflated price->MV; position and MV
   EMISSION still writes per event. Same per-key timer pattern on output
   emission (100-250 ms snapshots) slashes sink work; validation stays
   green by the same final-state argument as Phase 7.
3. Partitions 16->32 + sink batching (linger/batch.size/lz4).
Excluded: binary serialization (3-5x known) — changes the workload, breaks
parity with the Confluent test which also paid the JSON tax.

PLAN
----
10.1 Baseline: redeploy stack, backlog-drain at P=12 as-is -> true current
     AWS ceiling (est. 140-210k).
10.2 Rung A (config only): partitions=32, sink batching/compression,
     ParallelismPerKPU=2-4 on the same 12 KPUs -> re-drain.
10.3 Rung B (code): conflated emission on position/MV outputs; make test +
     validation green; re-drain.
10.4 Verdict table: msgs/s, units, $/hr, msgs/s-per-dollar, both clouds,
     same drain methodology. Target: >=232k on <=12 KPUs.
10.5 Only if tuning falls short: add KPUs last, report honestly.
10.6 Teardown, verify zeros, squash-merge, tag Phase-10. Est. cost ~$5.

Review gates: plan (approved "go ahead") -> baseline result before config
changes -> Rung A result before code changes -> results before teardown.

FOLLOW-UP (user, mid-phase): "we should tune and see the max we can get out
of the P=12" -> "lets do all the tuning then prove the lowest cost where

Refined goal: after tuning, walk KPUs DOWN (12 -> 8 -> 6) and find the

-> "we should prove at the end we can still scale up linearly with all the

10.3b required" — take the cheapest passing config from the descending
ladder and prove ONE scale-up doubling (~2x KPUs -> ~2x throughput, ±15%);
ladder rungs corroborate as midpoints.

RESULTS SO FAR
--------------
10.1 BASELINE (P=12, 12 KPUs, untuned, 136M-record drain, zero restarts):
  peak minute 483,082 msgs/s (2.1x Confluent's 232.7k); whole-drain avg
  ~236k; 4 consecutive minutes >= 232k; full-pipeline (both topics
  draining) phase ~210-255k; totals cross-checked exactly (138M vs 136M).
  12 KPUs $1.43/hr vs Confluent 16 CFUs $3.36/hr -> ~4.9x throughput/$.
  ANSWER to the phase question: zero extra KPUs needed. Phase 8's 110k was
  never a ceiling — generator-fed at 52% busy.
  Measurement lesson re-learned: CloudWatch merges subtasks into one
  series; rate = series value x parallelism (validated exactly against
  generator counts, twice).
  First drain attempt had 6 restarts (startup transients) and an
  undersized backlog — thrown out, re-run clean.

New deployment gotchas (for the runbook):
  - Partial terraform apply race: MSF app update failed (FORCE_STOPPING)
    AFTER ECS task-def/service updated -> a task launched with stale args.
  - Generator IAM needed kafka-cluster:DeleteTopic + AlterTopic for the
    new topics.recreate / partition-grow support.

RESULTS (all drains: same backlog-drain method as Phase 9's Confluent test,
rates = CloudWatch merged-series x parallelism, totals cross-checked
against generator counts)
--------------------------------------------------------------------------
TUNING AT FIXED COST (12 KPUs, $1.43/hr):
  untuned baseline:        ~230k sustained (peak 483k price-only tail)
  Rung A (config only):    ~319k sustained mixed  (+39%)
    P=24 via ppkpu=2, 48 partitions, sink linger=25ms/batch=256KB/lz4
  Rung B (+code):          ~435k sustained mixed  (+89% vs baseline)
    emit.interval.ms=250 conflated output emission (PositionAggregator +
    TickerPositionAggregator; default 0 = per-event, latency unchanged);
    3 new harness tests, 21 total green; bottleneck had been the four
    sink tasks pinned at 897-1000 ms/s busy with backpressure to sources.

DESCENDING COST LADDER (tuned, vs Confluent 232.7k @ $3.36/hr compute):
   8 KPUs $0.99/hr: peak 199k  FAIL (sub-linear below 10: 24.9k/KPU)
  10 KPUs $1.21/hr: peak 352k, 5 consecutive min >= 232.7k  <- THE FLOOR
  12 KPUs $1.43/hr: ~435k sustained (36k/KPU)
  20 KPUs $2.31/hr: peak 757.6k, top-3 avg ~650k

LINEARITY (user requirement, from the floor): 10 -> 20 KPUs = 2.0x
sustained (325k -> 650k top-3 avg), peak 2.15x. The dial survives all
tuning.

VERDICT: AWS matches Confluent's peak at $1.21/hr vs $3.36/hr — 64%
cheaper compute — and at equal spend does ~4x the work (~291-328k msgs/s
per $/hr vs Confluent's ~69k). Emission conflation is the single biggest
lever (+36% alone); it ships default-off (emit.interval.ms=0) so the
latency guarantee of Case 1 is unchanged unless explicitly traded.

More gotchas found (runbook): CloudWatch merges subtask series (x
parallelism, validate against known totals); MSF metrics have a ~2-min
blind spot after job start (size backlogs to outlast it); terraform
partial-apply race also runs OLD-args ECS tasks; generator IAM needed
DeleteTopic/AlterTopic; a laptop DNS blip can fail an apply mid-plan
(retry is safe).
